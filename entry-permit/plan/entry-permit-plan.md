## 2b. Date and time rule (owner decision, 2026-11-06): dates are strings, no timezone math

**Every date and timestamp is plain text in Jakarta wall-clock time. The app never converts between time zones.**

- **Formats:** a day is `yyyy-mm-dd` (`CHAR(10)`); a moment is `yyyy-mm-dd hh:mm:ss` (`CHAR(19)`), in Jakarta local time with **no `Z`, no offset, no `T`**. Date of birth, visit dates, validity dates, planned arrival and departure are all days. Same convention as hse-medpost's tables.
- **Comparison** is plain string comparison (`<`, `>`, `=`), which sorts correctly in this format. MariaDB and SQLite both do it natively, so SQL needs no date functions.
- **Arithmetic** (add days, difference in days, add weeks, "14 days before", inclusive span) goes through one small `dates` package that works on the calendar only (year/month/day to a day number and back). It never touches a time zone or a `time.Time` in a location, so no hour of the day can shift a date.
- **"Today" and "now"** come from one function that reads the Jakarta wall clock once per request or job and returns the two strings. Tests inject a fixed "now" as a string.
- **Day counts that used elapsed time now use calendar days**: for example weeks on site = `floor((today - day of first check-in) / 7)`; the legacy version counted 24-hour periods from the check-in time, so the new count can differ by at most a day around the boundary hour (a check-in at 23:00 counts the next calendar day as day 1). Same-day = 1 inclusive day, as before.
- **The Cloudflare Worker follows the same rule**: it stops using `new Date()` for day tests and compares `yyyy-mm-dd` strings, with its "now" taken as Jakarta wall time. This removes the UTC-versus-Jakarta off-by-one before 07:00 (gate rules 3.1.4).
- **The one allowed conversion is at the import boundary, once:** timestamps in the old gate database are UTC ISO strings (`...T...Z`); the importer and the first sync pull convert them to Jakarta wall time (+7 hours) and store the string. Sheet cells exported from Excel are already wall-clock serial numbers, so they convert to text with no shift. Anything with an offset or `Z` seen after cutover is rejected as a bug.
- **Dates from outside** (forms, medpost API, emails) are validated as real calendar days (`2027-02-30` is rejected) and stored as given, never parsed through a date-time type.
- **Go types:** `dates.Day` and `dates.Moment` are string-based types, so a plain `time.Time` cannot leak into a rule function.

## 2c. Pages and navigation (owner decision 2026-11-06): one home page, one login

The old app had a separate welcome page per role (requester, reviewer, gate officer) and a URL per portal. The new app has **one home page at `/`**:

- **Requester (no login):** three tiles: **Work Entry Permit** (WEP/LEP, for workers, needs a valid MCU), **Visitor Entry Permit** (the visiting waiver, `WVR-`; the page says "also called a visiting waiver" so people used to the old word recognise it) and **Working schedule / ticket** (verify with LEP + date of birth, then propose a ticket). - **Landing rule:** a user with one role goes to that role's page. A user with several roles lands on the highest-priority one (admin, final, stage1, doctor, gate officer, dashboard-only) and sees links to their other pages in the header.

- **Dropdown privacy:** the dropdown lists display names of active staff only (no roles, no emails); the PIN lockout (5 tries / 15 min, per account) protects the accounts. Same exposure as medpost today.

## 3b. Position lookup (`resolvePosition`), read from `Code.js` and the sheet data

A job title typed by the requester (the site title; the MCU title only if blank) is normalised and resolved in this order. The first layer that matches wins:

1. **Exact alias** (sheet cols A-G): alias text equals the title -> canonical position, category, risk tier, certificate name, `CertRequired`.
2. **Keyword rules** (cols J-M, 38 rows): any comma-separated keyword is *contained in* the title -> mapped canonical position + risk tier; certificate info is then taken from that canonical position's **first** layer-1 row.
3. **Classification rules** (cols Q-T, 19 rows): same contains-match -> `Executive` / `Management` / `Professional` / `Support`, risk `LOW`, certificate never required.
4. No match -> position kept as typed, `CertRequired = N#A`. Result then goes through `applyPerpetualCertValidity_`.

Tables: `PositionCanonical` (No, Category, RiskTier, Name, CertificateName, CertRequired), `PositionAlias` (alias -> canonical), `PositionKeyword` (priority, keywords, canonical, risk tier), `PositionClass` (priority, keywords, classification, risk tier). Rule order is explicit and editable (priority column), because order decides the winner.

Things to carry over exactly, then clean up on purpose, not by accident:
- **Match semantics are "contains", not whole word** (for example keyword `it` or `hr` can match inside longer words). Port exactly so imported permits resolve the same, cover it with golden tests, and list a word-boundary option as a later decision for the owner.
- **`CertRequired` is stored on every alias row, and the alias path uses that row's value**, while the keyword path uses the canonical's first row. The data disagrees with itself: for Banksman / Signalman the first alias is `Y` and the rest `N`; Electrician, Insulation, Pump, Hazmat, Steel Erector, Carpenter and others are `N` although a certificate is named. The new model keeps `CertRequired` on the canonical position (one value). The importer reports every canonical position whose alias rows disagree, and the owner picks the value once.
- Cert rules later feed the `CertificateRequired` form toggle.
- The pasted data was cut off after about 40 canonical positions (it stops in the Pressure Vessel Technician rows), so the full list comes from the phase-0 sheet export, not from the chat.

## 4. The three design questions that are not mechanical

### 4.1 MCU lookup (`QueryMCU`, `lookupMCU`, `getMCUForPermit`)

The legacy app copies MCU results into its own sheet. hse-medpost already holds the real `McuRecord`s and exposes a bearer-token **directory API** (`internal/directory`, `DIRECTORY_API_TOKEN`, a `checkups.go` route already exists). Recommendation: entry-permit asks medpost over loopback HTTP (`127.0.0.1:8113`) for name + DOB (+ checkup id) -> validity, result, company, position; it does **not** read medpost's database and keeps no copy. Phase 0 verifies the existing checkups route returns what `lookupMCU` needs; any gap becomes a small, token-guarded addition in medpost, planned there. LEP validity then stays `MCU valid until - graceWeeks x 7 days`.

**Update 2026-11-06 (owner): the same API also supplies the worker's identity, company and position.** The WEP form no longer asks the requester to type name, date of birth, nationality, NIK/passport, company, entity, parent or position: the requester searches and picks the worker, and those arrive read-only from medpost's employee record (`patientId`, name, gender, DOB, nationality, `personalId`, company, `companyEntity`, `parents`, `workPosition`, and the MCU fields). Gap found in medpost: `personalId` is on the `checkups` route but **not on the `employees` route**; a small token-guarded addition is planned in medpost. `PersonalID` (unique there) becomes the person key for duplicate and renewal checks. Waiver visitors are not employees, so the waiver form keeps its own typed identity. Details: `plan/business-rules-permits.md` section 0.

### 4.2 Gate stays on Cloudflare, synced every 5 minutes (decided 2026-11-06)

The scanner keeps running on the Worker + D1, so site entry does not depend on the Pi. The Pi is the source of truth for permits; D1 is the source of truth for gate events.

- **Who starts the sync: the Pi.** A `gatesync` job on the Pi calls the Worker over HTTPS every 5 minutes. Nothing on the Pi is exposed to the Worker, and the shared secret (`SYNC_SECRET`, already used today) lives in the Pi's `.env`. This reverses today's direction, where Apps Script pushes, but the Worker's existing push/pull endpoints and chunking (about 40 rows per call, D1 `batch()`) are reused.
- **Pi -> D1 (push):** active permits and waivers (LEP, name, company, validity dates, status, `Resigned`), reference lists (gate officers and codes, gate names, checkout reasons). Send only rows changed since the last acknowledged sync (`UpdatedAt` column), not the whole table.
- **D1 -> Pi (pull):** new `gate_log` rows and changed `gate_state`, each acknowledged after the Pi has committed them. Insert is idempotent on the Worker's event id, so a retry after a crash never duplicates a log row.
- **One writer per table** avoids merge conflicts for permits (Pi) and gate state / gate log (gate). **Tickets are the exception: both sides write them**, with field-level ownership (the Pi owns the plan and the lock; the gate owns first check-in `record_start` and the closing at check-out). Full table and conflict rule: `plan/business-rules-gate-jobs.md` section 5. The Worker's existing sync endpoints are reused as they are, now called by the Pi.
- **Pi derives** `TotalActualDays`, the ticket's `RecordStart`, and the dashboard's Active/Gate Activity from pulled events.
- **What 5 minutes costs:** a newly approved LEP can be refused at the gate for up to 5 minutes, a `Resigned` mark takes up to 5 minutes to block entry, and the dashboard's Active list lags. Mitigation: an "approved" or "resigned" change triggers an immediate extra push instead of waiting for the next tick. Confirm the officers accept the delay for the rest.
- **If the Pi is down:** gate keeps working on the last pushed data; the sync resumes and catches up from the acknowledgement marker. The dashboard and approvals are the only things that stop.
- **Monitoring:** the sync records last success time in `JobRun`; the admin page shows it and warns when older than 15 minutes.
- Camera QR scanning needs HTTPS, which the Worker already provides.

## 5a. Working in 5-hour sessions (Claude Pro): build in slices

The phases above are too big for one window. Each phase is cut into **slices**: one slice = one session = one commit, small enough to finish before the limit. The exact Pro limit is not known to me and changes with model and message size, so these are sized conservatively; if a slice finishes early, take the next one.

Session rules:
1. **Start:** "Read `plan/entry-permit-plan.md` Progress Log and do slice N." Nothing else needs re-explaining, because the plan and the tests are the memory.
2. **Never read `Code.js` whole** (12k lines). Slice 0b-0d turns it into `plan/business-rules-*.md` once; later slices read those files plus targeted line ranges (`grep -n`, `graphify query`).
3. **Test first, and the failing tests are the handoff.** If the window ends mid-slice, commit work-in-progress with tests marked failing, and write what is left in the Progress Log.
4. **No subagents inside a slice** (each starts cold and re-reads context). Run one code review + security review per phase, not per slice. This deliberately batches the reviews the global rules ask for after every change; say if you want them per slice instead.
5. **One concern per slice**, `/clear` between slices, use the Sonnet model for build slices (keep Opus for phase-0 rule extraction if you want extra care).
