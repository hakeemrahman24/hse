# hse-medpost — consolidate medical-activities, entry-mcu, and a new EMR module into one app

## Context

Today each app on the orangepi3b (`hse-workpermit`, `hse-observation`, `medical-activities`, and the still-scaffolded `entry-mcu`) is strictly one database + one Go binary, no sharing. That pattern breaks down for the first-aid-post domain: `medical-activities` tracks the team's program work (inspections, staff roster, documents) and has zero patient data; `entry-mcu` tracks one-off MCU checkup events with demographics re-entered on every row and no persistent patient identity; and there is no first-aid/walk-in visit or medication-dispensing concept anywhere yet.

The user wants a real first-aid-post system: one shared database covering `medical_activities`, `entry-mcu`, and a new `emr` module, with genuine foreign keys between them — an EMR entry references the same patient a checkup references, and the same staff roster used by `medical-activities` treats patients in the EMR. Decided in discussion:

- **One shared MariaDB database**, not three databases linked by convention.
- **Extract a real `Patient` entity** out of `entry-mcu`'s per-checkup demographic columns, so checkups and EMR entries both reference `FK_PatientID` instead of duplicating name/DOB/company per row.
- **`emr` scope**: first-aid/walk-in encounters (complaint, diagnosis, treatment, staff who treated) plus medication/inventory dispensing per encounter.
- **Routine screenings are separate from `emr`**: alcohol test, drug test, fatigue survey, and pre-shift vital signs check are periodic per-worker screenings, not ad-hoc illness/injury encounters — different cadence and result shape, so each gets its own table (`AlcoholTestTable`, `DrugTestTable`, `FatigueSurveyTable`, `VitalSignsCheckTable`) rather than being folded into `EmrTable` with a type discriminator. All four reference the same `Patient`/`MedpostStaffTable` FKs as everything else, and map onto program entries (`DrugAndAlcoholTesting`, `FatigueManagementProgram`) that already exist in `medical-activities`' `HealthProcedureTable` — these become the actual per-worker record of a program that currently only logs program-level activity.
  - **Forward-compat note**: `AlcoholTestTable` and `DrugTestTable` stay separate now (YAGNI — no combined-kit requirement exists yet), but if on-site testing later moves to a combo breathalyzer/saliva kit reporting both in one pass, merging them later is a straightforward migration — both tables already share the same `FK_PatientID`/`FK_StaffID`/date shape, so a future `SubstanceScreeningTable` could backfill from both by matching patient + same-day test date, then the two old tables drop. Not designed in now, just noted so the later merge isn't a surprise.
- **`medical-activities` gets fully merged**, not left standalone — accepted the cost of porting its already-deployed Go binary/auth into the new consolidated app, because a shared DB with real FKs to `MedpostStaffTable` requires it to actually live in the same schema, and splitting staff/login into two systems means two rosters to keep in sync.
- **Name**: deliberately not "clinic" anything — in Indonesia "klinik" is a regulated facility class (Permenkes licensing, medical director requirement), while this is a workplace first aid post (Pos P3K), a lower-bar facility type. Landed on `medpost` (short, avoids the word "clinic" entirely) then refined to **`hse-medpost`**: two words, matches the `hse-` prefix its siblings (`hse-workpermit`, `hse-observation`) already use, groups it with the same app family at a glance. Database name follows the same underscore convention those two use: `hse_medpost` / `hse_medpost_user`. This extends to internal SQL identifiers too: the carried-over `ClinicStaffTable` name is renamed to `MedpostStaffTable` during the port (same table, same columns — name only), so no "clinic" term survives anywhere in the new app, code, or UI.

Outcome: a single new project, `hse-medpost/`, one Go binary, one MariaDB database, one login, replacing the standalone `medical-activities` deployment and superseding the `entry-mcu` scaffold.

Nothing in `_reference/` is imported directly — code gets copied/rewritten into `internal/`/`web/` at port time (step 5).

`internal/README.md` and `web/README.md` are the up-to-date per-folder documentation; this plan stays the authoritative source for the *reasoning*.

## 2. Target schema (single `hse_medpost` database)

Table naming/conventions carried over exactly as both existing schemas already use them: PascalCase table names, `FK_` prefix, `<Table>ID` PK, `CHAR(10)`/`CHAR(19)` text for all dates/timestamps (never `DATE`/`DATETIME`), `ENGINE=InnoDB`, date/business rules enforced in Go not SQL `CHECK` (ASUSTOR/older-MariaDB compatibility precedent).

### Common (shared across all three modules — see `internal/README.md` for the package-level ownership index)

**Reference data** (from `entry-mcu/plan/sql schema`, unchanged in shape, reseeded with real values — see §Settings page):
- `EntityType`, `Company`, `CompanyRelation` — now global to the whole app, not entry-mcu-only, since `Patient.FK_CompanyID` and MCU/EMR records all resolve against the same company list. Real production seed data for all three now exists (given during the Settings-page discussion) — use it directly at migration step 3/4 instead of guessing values from the Sheet export.

**New lookup tables** — admin-editable via Settings (see §Settings page), so each is a real table, not an inline `ENUM`: an `ENUM` can't be edited from an admin form without an `ALTER TABLE`, which is exactly the manual-SSH schema-change risk this project's own docs warn about elsewhere.
```sql
CREATE TABLE NationalityTable (
    NationalityID INT AUTO_INCREMENT PRIMARY KEY,
    Name    VARCHAR(64) NOT NULL UNIQUE,
    Status  ENUM('Active','Archived') NOT NULL DEFAULT 'Active'
) ENGINE=InnoDB;
-- seed: Indonesia, Philippines, Malaysia, Singapore, USA, UK, China

CREATE TABLE CheckUpCriteriaTable (
    CheckUpCriteriaID INT AUTO_INCREMENT PRIMARY KEY,
    Name    VARCHAR(64) NOT NULL UNIQUE,
    Status  ENUM('Active','Archived') NOT NULL DEFAULT 'Active'
) ENGINE=InnoDB;
-- seed: Pre Employment, Annual, Bi-annual, Fit for Task, Follow Up, Exit

CREATE TABLE TaskCategoryTable (
    TaskCategoryID INT AUTO_INCREMENT PRIMARY KEY,
    Name    VARCHAR(128) NOT NULL UNIQUE,
    Status  ENUM('Active','Archived') NOT NULL DEFAULT 'Active'
) ENGINE=InnoDB;
-- seed: Remote Site Worker, Non Remote Site Worker/Jakarta Office, Heavy Equipment or
-- Crane Operator, Work at Height, Confined Space or SCBA/Respirator Users, Professional
-- Drivers, Work in Extreme Temperature, Fire & Emergency Crew, Food Handler, Health
-- Professionals, Shift Worker, Business Travelers, Other Professional (Pilot, Seafarer,
-- Diver), Remote Site Visitor

CREATE TABLE NotificationEmailTable (
    NotificationEmailID INT AUTO_INCREMENT PRIMARY KEY,
    Email          VARCHAR(255) NOT NULL,
    RecipientType  ENUM('To','Cc') NOT NULL DEFAULT 'To',
    Notes          VARCHAR(255) NULL
) ENGINE=InnoDB;
-- What triggers sending to this list is a separate, later decision (not designed here) —
-- this is just the recipient list itself.
```
`CheckUpCriteriaTable`/`TaskCategoryTable` are entry-mcu-specific (only `McuRecord` references them — see below); `NationalityTable`/`NotificationEmailTable` are common (`Nationality` via `Patient`, `NotificationEmailTable` is a whole-app setting owned by no single module).

**New: `Patient`** (extracted from `McuRecord`'s inlined demographics):
```sql
CREATE TABLE Patient (
    PatientID       INT AUTO_INCREMENT PRIMARY KEY,
    Name            VARCHAR(255) NOT NULL,
    Gender          VARCHAR(16)  NULL,
    DateOfBirth     CHAR(10)     NULL,
    FK_NationalityID INT NULL,
    BloodType       VARCHAR(8)   NULL,
    EmployeeID      VARCHAR(32)  NULL,   -- badge/NIK if one exists; nullable, see open question below
    FK_CompanyID    INT NULL,
    WorkPosition    VARCHAR(128) NULL,
    INDEX idx_patient_name (Name),
    FOREIGN KEY (FK_CompanyID) REFERENCES Company(CompanyID)
        ON UPDATE CASCADE ON DELETE SET NULL,
    FOREIGN KEY (FK_NationalityID) REFERENCES NationalityTable(NationalityID)
        ON UPDATE CASCADE ON DELETE SET NULL
) ENGINE=InnoDB;
```
`McuRecord` and `EmrTable` both gain `FK_PatientID` and drop their own copies of Name/Gender/DateOfBirth/Nationality/BloodType. Per-checkup measurements that genuinely vary over time (`Age`, `HeightCm`, `WeightKg`, `WorkPosition`/`FK_CompanyID` at time of that specific checkup) stay on `McuRecord` as point-in-time snapshots — only the stable identity fields move to `Patient`.

### Per-module tables

**`entry-mcu` module**: `McuRecord`, finalized against the real 71-column legacy Google Sheet header (the draft above was a guess made without seeing it — see `migrations/006_entrymcu.sql` for the authoritative DDL). Column-by-column mapping and every discrepancy from the original guess is recorded in that migration file's header comment; the key deviations from the earlier draft:
- `FK_PatientID` (not null), `FK_CheckUpCriteriaID` (replaces free-text `CheckUpCriteria`), `FK_TaskCategoryID` (replaces free-text `TaskType` directly — same normalization, not a separate new field alongside a kept legacy column).
- `FK_CompanyRelationID` replaces the legacy `RelationCode`+`RelationDepth` pair — `CompanyRelation` already owns `Depth`, so it's not duplicated here; join through the FK instead.
- `IsTerminal` (not `IsNonTerminal`) — renamed and polarity-corrected so `TRUE` (default) means "current/counted", `FALSE` means "superseded by a renewal or newer follow-up", matching the real sheet's `Terminal` column semantics directly instead of double-negating.
- `HealthCertificateFileName` is plain text (no upload/storage wiring this pass).
- `Age`/`HeightCm`/`WeightKg`/`WorkPosition`/`FK_CompanyID` stay as per-checkup snapshots on `McuRecord` (unchanged from the original reasoning); all exam criteria/notes pairs stay flat columns, not a child table (unchanged — see `_reference/entry-mcu/plan/migration-to-mariadb.md` §3's original reasoning, reaffirmed after discussion).

Backend CRUD for `Patient`/`NationalityTable` (`internal/patient`) and `McuRecord`/`CheckUpCriteriaTable`/`TaskCategoryTable` (`internal/entrymcu`) is built and verified; the clinical entry form UI (replacing `web/templates/mcu.html`'s placeholder) is a separate follow-up pass. The legacy-Sheet→MariaDB import and the ongoing MariaDB→Sheet export-back job (for the `entry-permit` system's `IMPORTRANGE` dependency, admin-configurable via Settings — file ID, sheet name, sync period) are designed but not yet built; see the Progress Log entry below for the full design.

**New: `emr` module** (first-aid/walk-in encounters + medication dispensing):
```sql
CREATE TABLE EmrTable (
    EmrID             INT AUTO_INCREMENT PRIMARY KEY,
    FK_PatientID      INT NOT NULL,
    FK_StaffID        INT NOT NULL,        -- who treated, references MedpostStaffTable
    EmrDate           CHAR(10) NOT NULL,
    EmrTime           CHAR(19) NULL,       -- 'YYYY-MM-DD HH:MM:SS' text
    ChiefComplaint    TEXT NULL,
    Vitals            VARCHAR(255) NULL,   -- BP/temp/pulse/RR, free text to start (YAGNI on a vitals sub-table)
    Diagnosis         TEXT NULL,
    TreatmentGiven    TEXT NULL,
    FollowUpNeeded    BOOLEAN NOT NULL DEFAULT FALSE,
    ReferralNotes     TEXT NULL,
    EmrStatus         ENUM('Open','Closed','Referred') NOT NULL DEFAULT 'Open',
    FOREIGN KEY (FK_PatientID) REFERENCES Patient(PatientID)
        ON UPDATE CASCADE ON DELETE RESTRICT,
    FOREIGN KEY (FK_StaffID) REFERENCES MedpostStaffTable(StaffID)
        ON UPDATE CASCADE ON DELETE RESTRICT,
    INDEX idx_emr_date (EmrDate)
) ENGINE=InnoDB;

CREATE TABLE EmrMedicationTable (
    EmrMedicationID    INT AUTO_INCREMENT PRIMARY KEY,
    FK_EmrID           INT NOT NULL,
    FK_MedicationID     INT NOT NULL,
    QuantityDispensed   INT NOT NULL,
    Notes               TEXT NULL,
    FOREIGN KEY (FK_EmrID) REFERENCES EmrTable(EmrID)
        ON UPDATE CASCADE ON DELETE CASCADE,
    FOREIGN KEY (FK_MedicationID) REFERENCES MedicationTable(MedicationID)
        ON UPDATE CASCADE ON DELETE RESTRICT
) ENGINE=InnoDB;
```
Stock decrement on dispense is app-enforced (Go transaction: insert `EmrMedicationTable` row + decrement `MedicationTable.StockQuantity` together), matching the existing "business rules in Go, not SQL CHECK" convention.

> The `emr` design above is superseded in draft by [emr-plan.md](emr-plan.md): a `Visit` header with per-type detail tables (fatigue, malaria, wellness, outpatient), kept separate from the append-only form-submission tables. Nothing is built yet.

**New: `inventory` module** (medicine stock — separate package/table group from `emr` since it grows independently of any single encounter):
```sql
CREATE TABLE MedicationTable (
    MedicationID     INT AUTO_INCREMENT PRIMARY KEY,
    Name             VARCHAR(150) NOT NULL,
    Unit             VARCHAR(32)  NOT NULL,   -- tablet, ml, box, ...
    StockQuantity    INT NOT NULL DEFAULT 0,
    ReorderThreshold INT NULL,

```

**`medical_activities` module**: carried over from `_reference/activity-log/plan/sql schema`, colocated in `hse_medpost` instead of `medical_activities`, with one deliberate deviation from that source: `SubHeaderEntryTable`/`EntryEvidenceTable` are folded into `ActivityTable`/`EvidenceTable` via nullable `FK_SubHeaderID`/`FormLink` columns instead of staying a parallel table pair — a sub-header entry turned out to be structurally identical to a top-level activity (same date/title/description/staff/evidence shape), so it's just an activity scoped to a sub-header rather than its own table family. `ActivityType` has no equivalent in the old entry shape and gets backfilled to `'Monitoring/Inspection'`; `EvidenceTable` has no `'Document'` type (only `AttendanceList`/`ReportAttachment`/`Photos`), so migrated `'Document'` evidence maps to `'ReportAttachment'`. `internal/activity-log/migrate.go`'s `EnsureSubHeaderMerge` is the one-time upgrade path for pre-existing SQLite files. Of the resulting 9 tables, `MedpostStaffTable`, `AppUserTable`, and `PositionRoleTable` are classified as **common** (see above) despite living in this DDL block — they become the single login/staff roster for the whole app, used by `EmrTable.FK_StaffID`, the four screening tables' `FK_StaffID`, and (optionally, later) `entry-mcu`'s `Reviewer` field, currently free text — not required for this pass, YAGNI. The remaining 6 (`HealthProcedureTable`, `SupervisorTable`, `ActivityTable`, `EvidenceTable`, `DocumentTable`, `SubHeaderTable`) stay activity-log-only.

## 3. Settings page

Role-gated, same two-role split `AppUserTable`/`PositionRoleTable` already enforce (`admin` vs `staff`/`manager`):

- **Staff (any role)**: change their own username/password only — existing `PUT /api/me/password` pattern from `_reference/activity-log`, reused as-is.
- **Admin only**: everything else —
  - User credentials (add/edit `AppUserTable` entries)
  - Health programs (`HealthProcedureTable`) + subheaders (`SubHeaderTable`) under a program
  - Companies (`Company`) and company relations (`CompanyRelation`)
  - The four new lookup lists: `CheckUpCriteriaTable`, `TaskCategoryTable`, `NationalityTable`, `EntityType`
  - Notification email recipients (`NotificationEmailTable`, to/cc) — recipient list only; what triggers a send is a separate, later decision
  - `EntityType` — see §2, real seed values given: `Client, Contractor, Consultant, ManPowerSupply, Supplier, Government`

Real production seed data now exists for `Company` (54 rows) and `CompanyRelation` (48 rows) — captured verbatim during this discussion. Use it directly when applying the schema (step 4 below) instead of re-deriving it from the Sheet export.

## 4. Open question to resolve before the `Patient` migration step

`McuRecord` today has no stable external identifier — only `Name` + `DateOfBirth` + `Company`. Extracting `Patient` rows from existing `entry-mcu` Sheet data means deduping on that composite (best-effort: same name, same DOB, same company → same patient). If there's actually a stable badge/NIK number in use somewhere not yet captured in the sheet, that should become `Patient.EmployeeID`'s real source and the dedupe key — otherwise this is a genuine data-quality risk to flag before the load, not solve silently. Confirm during step 4 below; not blocking the schema/code work before it.

## 5. Migration steps

1. **Scaffold `hse-medpost/`** from `activity-log`'s existing structure (copy `internal/{auth,config,dates,display,middleware,storage}`, `web/`, `migrations/`, `systemd/`, build tooling as-is — these are domain-agnostic), then create the `internal/{patient,company,staff,activity-log,entrymcu,emr,inventory,screening}` subpackages.
2. **Write `plan/sql schema`** combining all groups above (reference data, Patient, entry-mcu, emr, screening records, medical_activities' 11 tables) plus the matching `migrations/001_sqlite.sql` dev schema.
3. **Migrate `medical-activities`' live data** into the new `hse_medpost` database — same DDL, straightforward dump/restore since nothing about those 11 tables changes.
4. **Migrate `entry-mcu`'s legacy Google Sheet data**, following the already-drafted steps in `entry-mcu/plan/migration-to-mariadb.md` §4, with one addition: a `Patient` extraction/dedupe pass runs *before* loading `McuRecord`, resolving the open question in §3 above.
5. **Port `medical-activities`' Go code**: most handlers move into `internal/activity-log` as a structural copy (not a rewrite, since the underlying tables don't change), but `staff.go`/`positions.go` move into the new `internal/staff` package instead, since `MedpostStaffTable`/`AppUserTable`/`PositionRoleTable` are common, not activity-log-specific — `admin.go`'s user-management pieces likely need the same split, decide exact boundary at port time. Also lift the shared `internal/{auth,storage}` and `web/` templates/static. Wire routes into `cmd/server/main.go` alongside the other domains.
6. **Build `entry-mcu`'s handlers** fresh (it was only ever a `/health`-only scaffold) in `internal/entrymcu`, plus `internal/patient` and `internal/company` for the shared identity/reference-data CRUD, against the refactored `McuRecord`/`Patient` schema.
7. **Build the new `emr` and `inventory` handlers/templates**: patient search/select (via `internal/patient`) and EMR encounter CRUD in `internal/emr`; medicine stock CRUD in `internal/inventory`; the dispense flow in `internal/emr` calls into `internal/inventory` for the stock decrement.
8. **Build the new screening handlers/templates** in `internal/screening`: alcohol test, drug test, fatigue survey, and vital signs check, each a simple patient-search + result-entry form against its own table.
9. **Cut over**: point whatever currently reaches `medical-activities:8113` at the new `hse-medpost` service instead; stand up `hse-medpost.service` under `~/.config/systemd/user/`; keep the old `medical-activities` service and `entry-mcu/google_sheet/` frozen as rollback until a full cycle of real usage is verified.
10. **Provision on the orangepi3b**: add `hse-medpost`/`hse_medpost`/`hse_medpost_user` to `~/Projects/setup-host.sh`'s app arrays (currently only lists the three older apps), create the DB + scoped user, retire `medical_activities`'s standalone DB/user once cutover is verified.

### 2026-10-28 — MCU portal: upload pipeline built (rebuild always, structure check, sandbox)
- **Built** in `internal/mcusubmit`: `pdfcheck.go` (`CheckStructure`: `%PDF-` at offset 0, refuses /JavaScript /JS /Launch /EmbeddedFile(s) /RichMedia /XFA /SubmitForm /ImportData /GoToE and /Encrypt, decodes `#xx` name escapes, inflates `/ObjStm` streams under a 32 MB total cap), `sandbox.go` (bubblewrap with no network and only the work folder, plus `prlimit` caps; falls back to limits only when bwrap does not work), `pdfrebuild.go` (Ghostscript always runs: a lossless pass, then the three shrinking passes of the activity uploads; every result must be a complete PDF, pass `CheckStructure` and keep the page count; smallest kept; fails closed with `ErrRebuild` or `ErrCannotShrink`), `filestore.go` (`FileStore` + `LocalDiskStore`, mode 0600, random refs, traversal refused), `ingest.go` (`Pipeline.Ingest`: 15 MB cap → check → optional `Scanner` on the original → rebuild → store; the upload is never stored and temp files are always removed).
- **Why not `CompressPDF`:** it skips files under 1 MB and keeps the upload on any failure, right for activity photos, wrong for untrusted files.
- **Measured (gs 10.08, this machine):** forms and small scans shrink 20–35% on the lossless pass; a 580 KB scan → 238 KB lossless, 61 KB at 100 dpi. Rebuild takes 0.1–0.25 s per file here; the Pi will be slower. Some already-small vector PDFs do not shrink further. The 1 MB target can still fail on big scans, so the submitter gets a clear "too large" message.
- **Found:** Ghostscript 10.08 keeps a catalog-level URI action (`/OpenAction` with `/URI`) in its output. Link annotations, forms and scripts are gone. The guarantee is "nothing that runs code", not "no actions".
- **Decision (owner): stored size limit is 2 MB for the portal** (`PortalTargetBytes`), not the 1 MB of activity uploads. Checked by eye on a 300 dpi dense scan: 150 dpi is fully readable, 100 dpi smears small grey print, so a higher limit keeps scans off the 100 dpi pass. Text and vector PDFs are never downsampled.
- **Virus scan:** left as an optional `Scanner` (none by default). After the rebuild the original is thrown away, so a scan adds an alarm, not protection. `clamd` costs about 1.1–1.3 GB RAM on the Pi; per-file `clamscan` loads the signature database each time.
- **Open:** run the pipeline on real PDFs on the Pi (gs 10.00 there; page counting uses the `bbox` device so it should not depend on the version); wire the pipeline into the upload page and `McuSubmission` rows; decide whether to add the ClamAV scanner.
